# 🍽️ אג'נט לתכנון תפריט בתקציב

## הסבר קצר

**הבעיה:** כשמארחים ארוחה משפחתית, צריך לאזן בין אילוצים שמתנגשים: לאחד יש אלרגיה לאגוזים, השני צמחוני, השלישית לא אוהבת פטריות, ויש תקציב. כל החלפה של מנה כדי לפתור בעיה אחת עלולה ליצור בעיה אחרת - המנה הזולה יותר מכילה גלוטן, המנה הצמחונית חורגת מהתקציב.

**למה בחרתי בה:** זו בעיה יומיומית שכל מי שמארח מכיר, והיא מתאימה לאג'נט ולא לתוכנית רגילה - אין סדר פעולות קבוע מראש. הצעד הבא תלוי במה שהתגלה בצעד הקודם.

**מה האג'נט עושה:**
1. **מקבל מטרה** - בשפה חופשית ("12 איש, 300 שקל, אחותי טבעונית") או כקובץ: מי מגיע, תקציב, אלרגיות, תזונה ומה כל אחד לא אוהב.
2. **מחליט בעצמו** איזה כלי להפעיל: לחפש מנות, לחשב עלות, לבדוק את האורחים, לבקש הצעות להחלפה או לאשר תפריט.
3. **בוחן את התוצאה ומשנה כיוון:** חורג מהתקציב - מחליף את המנה שחוסכת הכי הרבה. לאורח אין מה לאכול - מחליף מנה עיקרית.
4. **יודע מתי לעצור:** מצליח רק כשהכלי `finalize_menu` אישר את התפריט, ומפיק רשימת קניות. אם אין פתרון - מדווח למה ומה הכי קרוב שהגיע. גם ההצלחה וגם הוויתור נבדקים בקוד, לא לפי מה שהמודל אומר.

## מבנה האג'נט

| חלק | במימוש |
|---|---|
| **מוח** | מודל שפה עם function calling, דרך ספריית `openai` (נבדק עם Gemini, ראו הוראות הפעלה) |
| **כלים** | `search_recipes`, `calculate_cost`, `check_guests`, `suggest_swaps`, `finalize_menu`, `report_failure` |
| **לולאה** | עד 15 צעדים: המודל בוחר כלי (או כמה במקביל) ← הקוד מריץ ← התוצאה חוזרת למודל |

## הדגמה

ריצה מלאה: [demo/run_friday_dinner.txt](demo/run_friday_dinner.txt). קטע ממנה - כך נראית קבלת ההחלטות:

```
── צעד 2/15
🔧 calculate_cost(עוף בתנור | סלמון בתנור | תפוחי אדמה אפויים | ירקות קלויים | סלט פירות)
   ← 288 ש"ח מתוך 146 ✗ חריגה של 142 ש"ח
── צעד 3/15
🔧 check_guests(...)
   ← ✗ [hard] יוסי: אין אף מנה עיקרית שמותר לאכול (עוף בתנור: לא צמחונית; סלמון בתנור: לא צמחונית)
── צעד 4/15
🔧 suggest_swaps(עוף בתנור | קארי עדשים | מג'דרה | ירקות קלויים | סלט פירות)
   ← הכי משתלם: להחליף את 'עוף בתנור עם תפוחי אדמה' ב-'שניצל עוף' (חוסך 21 ש"ח → 152)
── צעד 5/15
🔧 suggest_swaps(שניצל עוף | קארי עדשים | מג'דרה | סלט ירקות קצוץ | אבטיח קר)
   ← אין החלפה שמוזילה את התפריט
── צעד 6/15
🔧 finalize_menu(...)
   ← ✓ התפריט אושר
```

התפריט שאושר (136.76 ש"ח) הוא בדיוק התפריט התקין הזול ביותר שקיים.

ריצה שבה אין פתרון: [demo/run_impossible_budget.txt](demo/run_impossible_budget.txt). האג'נט מוזיל את התפריט עד ש-`suggest_swaps` מראה שאין עוד מה להוזיל, ורק אז מדווח שהתפריט הזול ביותר עולה 123 ש"ח - בדיוק המינימום האפשרי.

מטרה בשפה חופשית, מהטקסט ועד רשימת הקניות: [demo/run_free_text.txt](demo/run_free_text.txt).

## הוראות הפעלה

דרוש Python 3.10 ומעלה.

```bash
pip install -r requirements.txt
```

**מפתח API:** מעתיקים את `.env.example` לקובץ בשם `.env` ומכניסים מפתח.
- **Gemini (חינמי):** יוצרים מפתח ב-https://aistudio.google.com/apikey. הקובץ כבר מוגדר לזה. כל הבדיקות וההדגמות רצו מול Gemini.
- **OpenAI:** מוחקים את השורה `LLM_BASE_URL` ומשנים את `LLM_MODEL` ל-`gpt-4o-mini`. הקוד משתמש בספריית `openai` הרשמית ובממשק function calling שלה, אבל לא הורץ בפועל מול השרתים של OpenAI.

המפתח נשמר רק ב-`.env`, שלא עולה ל-Git.

**הרצה:**

```bash
python llm.py                                    # בדיקה שהחיבור למודל עובד
python agent.py --ask                            # שואל מה התוכנית, בשפה חופשית
python agent.py --goal "10 איש, 150 ש\"ח, אחותי טבעונית"   # מטרה בשפה חופשית בשורה אחת
python agent.py                                  # ארוחת שישי מקובץ (examples/friday_dinner.json)
python agent.py examples/impossible_budget.json  # מקרה שאין לו פתרון
```

במטרה בשפה חופשית, האג'נט מציג איך הבין את הבקשה ומבקש אישור לפני שהוא מתכנן. אם חסר מידע (כמה סועדים? מה התקציב?), הוא שואל. עם `--yes` הוא ממשיך בלי לשאול, אבל רק אם אין אזהרות.

אפשר גם ליצור בקשה בקובץ JSON באותו מבנה כמו בתיקייה examples. אלרגיות אפשריות: `gluten`, `eggs`, `dairy`, `nuts`, `fish`. תזונה: `vegetarian`, `vegan`.

**צ'אט (לא חובה):**

```bash
python -m streamlit run chat.py
```

כותבים לאג'נט כמו בצ'אט. הוא מציג איך הבין, שואל כשחסר מידע, מתכנן אחרי אישור (את הצעדים אפשר לפתוח ולראות), ועונה עם תפריט ורשימת קניות. אחרי התפריט אפשר להמשיך לבקש ("בלי סלמון"), ואם אין פתרון - הוא מציע כמה להגדיל את התקציב.

**ממשק בדיקה (לא חובה):**

```bash

```

ממשק שבו רואים כל צעד של האג'נט בזמן אמת, מריצים 18 תרחישי קצה ומקבלים פסק דין מ"שופט" אוטומטי (ראו בהמשך).

**בדיקות אוטומטיות** (בלי אינטרנט ובלי מפתח):

## החלטות תכנון

- **המודל מחליט, הקוד מחשב ובודק.** מודלי שפה טועים בחשבון ולפעמים "שוכחים" אילוץ. לכן המחירים והבדיקות נעשים בכלים, והמודל רק בוחר מה לנסות.
- **הצלחה נקבעת בקוד.** המשימה מסתיימת בהצלחה רק כש-`finalize_menu` בודק מחדש את הכל ומאשר. אם המודל כותב "סיימתי" בלי אישור, הקוד מבקש ממנו להמשיך.
- **גם ויתור נבדק בקוד.** כשהמודל קורא ל-`report_failure`, הקוד בודק אם לתפריט הזול ביותר שנבדק יש עוד החלפה שמוזילה אותו. אם יש, הוויתור נדחה והמודל מקבל הסבר מה לנסות. הוספתי את זה אחרי שראיתי שהמודל מוותר גם כשהכלי אומר לו במפורש שיש עוד אפשרות - הוראה ב-prompt היא בקשה, לא חוק.
- **`suggest_swaps` במקום ניחוש.** בגרסה הראשונה המודל ניחש איזו מנה להחליף, ולפעמים בחר מנה שייקרה את התפריט. הכלי מחזיר לכל מנה את החלופות שמתאימות לכל האורחים, עם העלות אחרי ההחלפה. הכלי נותן מידע ולא פותר את הבעיה: הוא בודק החלפה של מנה אחת, וההחלטות נשארות אצל המודל.
- **אילוצי חובה מול העדפות.** אלרגיה וצמחונות - אסור בשום מקרה. "לא אוהב" - מותר עד מנה אחת שאינה עיקרית. אחרת, עם הרבה אורחים כמעט לא נשאר מה להגיש.
- **"אוהב/ת" - העדפה רכה.** האג'נט מנסה לכלול מנה עם מה שאורח אוהב, אבל אף פעם לא על חשבון אלרגיה, תזונה, "לא אוהב" או התקציב. היא לא משנה אם תפריט תקין - רק מדווחת ("❤️ דודה אוהבת חסה - יש בסלט חסה"). השופט מודד כמה העדפות נכללו מתוך כמה שהיה אפשר. הוספתי את זה אחרי שמודל פענח "דודה שאוהבת חסה" כ"לא אוהבת חסה" - כי לא היה לו מקום אחר לשים את המידע.
- **רשימת האורחים שמורה בקוד, לא נשלחת דרך המודל לכלים.** כך המודל לא יכול לשנות אותה בטעות.
- **טעות של המודל חוזרת אליו, לא מפילה את התוכנית.** שם מנה עם שגיאת כתיב מחזיר "אולי התכוונת ל...", JSON שבור או כלי לא קיים מחזירים הודעת שגיאה - והמודל מתקן. שגיאות שהאג'נט לא יכול לתקן (מפתח חסר, קובץ נתונים פגום) עוצרות מיד עם הסבר.
- **מחירים לפי מרכיבים.** מחיר מנה מחושב ממחירי המרכיבים שלה ומספר הסועדים. "כמהין" חסר בקטלוג בכוונה, כדי לבדוק שהאג'נט מתמודד עם מידע חסר.
- **נתונים מקומיים ולא סריקת אתרים.** כך הריצה צפויה ועובדת תמיד. הכלי `calculate_cost` מבודד את מקור המחירים, כך שאפשר להחליף אותו במקור חי בלי לגעת באג'נט. המחירים הם הערכה של מחירי סופר בישראל.
- **מגבלת צעדים ואזהרה לפני הסוף.** 15 צעדים מונעים לולאה אינסופית. כשנשארים 3, האג'נט מקבל אזהרה. הוספתי אותה אחרי שראיתי שבלעדיה הוא לא מוותר בעצמו גם כשאין פתרון.
- **עמידות לתקלות במודל.** בחריגה ממכסה לדקה - ממתין וממשיך. אם המודל לא זמין (עומס, השרת לא עונה, מכסה יומית) - עובר אוטומטית למודל הגיבוי הבא ב-`LLM_FALLBACK_MODELS`, ונשאר עליו עד סוף הריצה. הוספתי את זה אחרי שבמהלך הבדיקות השרתים של Gemini לא ענו או החזירו "high demand" כמה פעמים ביום. רק כשכל המודלים נכשלו - עוצר עם הודעה ברורה. שגיאה בבקשה עצמה (למשל מפתח לא תקין) לא מחליפה מודל, כי היא תחזור גם במודל אחר.

### מטרה בשפה חופשית ([goal_parser.py](goal_parser.py))

אותו עיקרון: המודל מפענח, הקוד בודק.
- **רשת ביטחון לאלרגיות.** הקוד סורק את הטקסט המקורי בעצמו (כולל קידומות בעברית: "לגלוטן", "ולביצים"). אם כתוב "צליאק" ואף אורח לא מסומן כאלרגי לגלוטן - הפענוח חוזר למודל לתיקון. אלרגיה שנשמטה בשקט היא הטעות הכי מסוכנת כאן. בבדיקות מצאתי שהמודל לפעמים כותב הגבלה רק ב"הנחות" ולא מסמן אורח, ולכן הסבר בהנחות לא נחשב.
- **אלרגיה שהמערכת לא מכירה לא ממופה למשהו אחר.** בוטנים הם לא אגוזים, וכשרות היא לא אלרגיה. הגבלה כזו מוצגת כאזהרה בולטת, ודורשת אישור של אדם - גם עם `--yes`.
- **המודל לא מחשב.** "40 ש"ח לאדם" מוכפל במספר הסועדים בקוד. בבדיקות המודל פענח "150₪" כ-150 לאדם, פי 6 מהתקציב. לכן הקוד דוחה "תקציב לאדם" אם בטקסט אין מילה כמו "לאדם" או "לסועד".
- **מה שחסר - שואלים, לא מנחשים.** בלי מספר סועדים או תקציב, האג'נט שואל.
- **אדם מאשר את ההבנה** לפני שמתחילים לתכנן, כולל ההנחות שהמודל עשה. בממשק אפשר גם לתקן אותה בטופס.

## איך בדקתי שהאג'נט טוב מספיק

[evaluate.py](evaluate.py) הוא "שופט": הוא בודק את כל ~4,200 צירופי התפריט האפשריים ויודע בוודאות מה התשובה הנכונה. כך אפשר לבדוק לא רק שהאג'נט רץ, אלא שהוא **צודק**: שמצא תפריט כשיש פתרון, ושוויתר רק כשבאמת אין.

זה אפשרי רק כי המאגר קטן. עם מאגר אמיתי החיפוש הזה לא אפשרי, ובשביל זה יש אג'נט. השופט משמש לבדיקה בלבד.

[scenarios.py](scenarios.py) מגדיר 18 תרחישים, ביניהם: תקציב שמאפשר רק תפריט אחד מתוך 288, כל חמשת סוגי האלרגיות יחד, אורחת שאלרגית לכולם, "קהל בררן" עם 9 מרכיבים לא אהובים, אילוצים סותרים שאין להם פתרון גם עם תקציב גבוה, תקציב שנמוך בשקל אחד מהמינימום, 50 סועדים וקלט לא תקין. את התקציבים כיילתי עם השופט, כך שברוב התרחישים נשארים רק 1-2 פתרונות.

```bash
python evaluate.py                          # כל התרחישים, עם פסק דין לכל אחד
python evaluate.py edge_budget --verbose    # תרחיש אחד, עם כל הצעדים
```

**השיפור, במספרים.** השופט הראה שבגרסה הראשונה האג'נט מגיע למסקנות נכונות "בערך", אבל מפספס פתרונות או מוותר מוקדם מדי. מדדתי את אותם שלושה תרחישים לפני ואחרי כל שינוי:

| גרסה | על הגבול | תקציב בלתי אפשרי | ארוחת שישי | ממוצע צעדים |
|---|---|---|---|---|
| ראשונה | ❌ פספס פתרון | ⚠️ ויתר מוקדם | ❌ נגמרו הצעדים | 14.3 |
| + `suggest_swaps` | ❌ נגמרו הצעדים | ⚠️ ויתר מוקדם | ✅ | 13.0 |
| + הפעלת כלים במקביל, בלי בדיקות כפולות | ✅ | ⚠️ ויתר מוקדם | ✅ | 9.7 |
| + בדיקת ויתור בקוד, החלפה כפולה | ✅ | ✅ | ✅ | 11.0 |

אחרי שהוספתי "אוהב/ת": **18/18 תרחישים** (gemini-3.5-flash-lite, ממוצע 6.1 צעדים). בשלושת התרחישים עם "אוהב/ת" האג'נט כלל את המקסימום האפשרי - גם כשהמקסימום היה 0 בגלל התקציב, או 1 מתוך 2 בגלל אלרגיה של אורח אחר.

לפני כן, כל 15 התרחישים עברו על שני מודלים שונים:
- **gemini-3.5-flash-lite:** 15/15, ממוצע 8.4 צעדים.
- **gemini-3.1-flash-lite** (מודל אחר וישן יותר, אחרי עדכון מחירים וכיול מחדש של התקציבים): 14/15 בריצה המלאה, ממוצע 6.3 צעדים. ארוחת שישי נעצרה בגלל שהשרת לא ענה בזמן (תקלה חיצונית, והמערכת עצרה עם הודעה ברורה), ועברה בהרצה חוזרת.

כל שורה בטבלה היא ריצה אחת, ומודל שפה לא מחזיר תשובות זהות בכל ריצה. לכן אלה מגמות ולא מדידה סטטיסטית.

## מגבלות

- כשיש תקציב, האג'נט מחפש תפריט **שעומד** בתקציב ולא את התפריט הזול ביותר. בתקציב נדיב הוא בוחר תפריט טוב, אבל לא בהכרח הזול ביותר. זה מכוון.
- `suggest_swaps` בודק החלפה של מנה אחת, ואם אין כזו שמוזילה - החלפה של שתי מנות יחד. בהחלפות בודדות בלבד, ב-11% מהבדיקות הוא "נתקע" מעל המינימום, כי חלק מהכללים מקשרים בין מנות. עם החלפות כפולות זה ירד ל-1 מתוך 336. כדי לא להיתקע אף פעם צריך לבדוק את כל הצירופים, אבל אז הכלי פותר את הבעיה במקום האג'נט.
- המודל לפעמים כותב בהסבר של `report_failure` תפריט שהוא לא באמת בדק. לכן הדוח הסופי מציג את התפריט שנבדק בפועל, לפי מה שהקוד שמר, ולא את מה שהמודל כתב.
- פענוח שפה חופשית לא יכול להיות מושלם - מודל שפה יכול להבין לא נכון. לכן ההבנה מוצגת לאישור, ורשת הביטחון בודקת את מה שהכי מסוכן (אלרגיות, תזונה, תקציב). היא לא בודקת למשל אם מספר הסועדים נספר נכון - את זה האדם רואה ומאשר.
- "כולם טבעונים" מפוענח כאורח טבעוני אחד. לפי הכללים, מספיק שאחת משתי העיקריות טבעונית, ולכן העיקרית השנייה יכולה להיות לא טבעונית - מנה שאף אחד לא יאכל.
- במסלול החינמי של Gemini יש מכסה יומית ומגבלה של 5 בקשות בדקה. ריצה צורכת 4-13 בקשות ויכולה לכלול המתנות.
